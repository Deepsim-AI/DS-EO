## Diagnosis: Model Concurrency Experiment (2026-08-13)

### 1. What TEST 1 established
**Test:** CTO (qwen3.6:35b) with laguna-xs-2.1 in standby, no spawn attempt.  
**Result:** CTO timed out at 30 seconds.

This was the critical finding. It established that **simply having another model's weights resident in unified memory is enough to cause the active model to time out**. The failure wasn't about spawning a new session or context thrashing — it's about shared memory bandwidth contention on Tegra's unified architecture. When two models' weights are mapped into GPU memory (even if only one is actively inferring), the memory bandwidth available for the active model's context buffers degrades to the point of timeout.

### 2. What TEST 2 established
**Test:** CTO + Reviewer with an explicit spawn of a separate session.  
**Result:** CTO timed out at 30 seconds (same as Test 1).

Confirmed Test 1's finding and added one more data point: spawning additional context buffers (system prompt, task tokens) on top of the already-degraded active model didn't make it worse or better — the timeout threshold is set by the weight-resident pressure, not the spawn itself.

### 3. What TEST 3 established
**Test:** Reviewer (laguna-xs-2.1:q4_K_M) alone, spawned as a fresh session.  
**Result: SUCCEEDED.**

This is the most important result for architecture design. It proves that **the 4-bit quantized model IS viable on this hardware** when it's the only active model. The Jetson AGX Orin can run laguna-xs-2.1 with full context. The constraint is specifically about **35B-class models** and their memory footprints, not about multi-model capability in principle.

### 4. What remains unknown (TEST 4 did not complete)
We never learned whether:
- `qwen3.6:27b` + Reviewer would work better than `qwen3.6:35b` + Reviewer (the size difference might be the answer)
- `ornith:35b` + Reviewer behaves differently from `qwen3.6:35b` + Reviewer (architecture differences between models could matter)
- The failure was truly due to model concurrency vs. OpenClaw context compaction (the session hit 123% tokens before TEST 4 could run, so we can't distinguish)

### 5. Architecture recommendation: sequential over concurrent — **YES, with nuance**

The evidence strongly supports switching DS-EO from concurrent multi-model agents to **sequential model residency with API-based inter-agent communication**. Here's why and how:

**Why:**
- The Jetson's unified memory architecture doesn't support two 35B-class models' weights simultaneously without measurable inference degradation
- Even standby weights cause active inference timeouts (Test 1)
- The smaller quantized model works fine alone (Test 3), so the Reviewer role is viable

**How to restructure:**
1. **CTO retains qwen3.6:35b as its primary model** — keep it loaded, don't unload during the workflow
2. **Reviewer uses laguna-xs-2.1 via CTO's API calls** (Option A from earlier analysis) rather than spawning a separate session — same model, zero spawn overhead, zero additional GPU memory pressure
3. **Unload models between phases** per AGENTS.md Section 3.5 rules — idle between planning and implementation, swap models for each role's turn
4. **Fix OpenClaw compaction thresholds independently** — the context overflow (123%) is a separate issue from model concurrency and must be addressed in config (reduce `keepRecentTokens`, tighten `reserveTokensFloor`)

**The key architectural insight:** The CTO should *query* the Reviewer model via its API endpoint, not *spawn* a Reviewer session. This achieves the same outcome (independent review) without the GPU memory penalty of concurrent inference contexts.
